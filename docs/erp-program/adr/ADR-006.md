# ADR-006: Event architecture and message broker

| Field | Value |
|---|---|
| Status | ACCEPTED (2026-10-19, approved by the owner, D-038) |
| Approvers | Chief architect; technical lead; DBA |
| Review by | 2027-04-19 |
| Part | 02 (REQ-ARCH-F02 to F13) |

## Context
Events carry business facts between modules (AC-5). The outbox must be written in the same transaction as the business change. Volumes are moderate: the design point is in §10.3 and does not require streaming.

## Decision drivers
- Exactly-once business effect through the inbox (AC-5)
- Replay and dead-letter handling
- Operational simplicity at the start

## Options considered
| Option | Assessment |
|---|---|
| Transactional outbox in PostgreSQL, relayed to a Redis-backed queue (BullMQ, proposed for v1) | Keeps the outbox in the transactional store; queue on Redis, which is already needed for cache and rate limits. |
| RabbitMQ | Mature routing; a second stateful system to operate. |
| Kafka | Built for very high streaming volume; not needed at the §10.3 design point; large operational cost. |

## Decision
Outbox table in PostgreSQL (written in the business transaction); a relay publishes to a Redis-backed queue (BullMQ) with consumers that use an inbox table for idempotency. Events follow <code>.<entity>.<past_tense_verb> with the AC-5 envelope. Kafka is rejected for v1 and may be reconsidered only with measured volume evidence.

## Consequences
- Ordering is guaranteed per aggregate, not globally.
- Schema registry and event versioning are built with Part 10.

## Fitness function
Event catalogue completeness check (EVENT_CATALOGUE.md) and a replay test per consumer (Part 10).

## Rollback
The relay can be replaced behind the same outbox table; the outbox is the stable contract.
