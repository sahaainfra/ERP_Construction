# ADR-002: Tenancy and data isolation

| Field | Value |
|---|---|
| Status | PROPOSED |
| Approvers | Chief architect; DBA; security architect; product owner |
| Review by | 2027-04-19 |
| Part | 02 (REQ-ARCH-F02 to F13) |

## Context
A tenant is a company group; companies and projects sit inside it (Part 00 §8, SE-8). Construction groups may need regulated isolation for some clients. Isolation must hold even if an application check is missed.

## Decision drivers
- Isolation enforced below the application layer
- Backups and restores per tenant
- No noisy-neighbour failure across tenants

## Options considered
| Option | Assessment |
|---|---|
| Shared schema, tenant_id, PostgreSQL row-level security (proposed default) | Cheapest to operate; RLS enforces scope in the database; one migration path. Needs careful indexing and connection context. |
| Schema per tenant | Clearer restore per tenant; migrations multiply by tenant count. |
| Database per tenant | Strongest isolation and restore; highest cost; used only for clients that require it. |

## Decision
Default: one shared schema with tenant_id on every business table and PostgreSQL row-level security. Regulated or very large tenants may move to a database per tenant later under the same schema. The existing single-tenant data (none in this repository) maps to a default tenant.

## Consequences
- Every business table carries tenant_id (constitution §7.2).
- Application code sets the tenant context per request; RLS is the backstop, not the only check.

## Fitness function
Planned test (Parts 03 and 07): a request from tenant A cannot read or write a tenant B row through any API or direct query with the context set. Not runnable yet: no database exists (Part 01 DB_ENTITY_MAP.csv is header only).

## Rollback
Schema-level rollback by dropping the RLS policies and tenant_id columns before any data is written; reversible until the first production tenant is loaded.
